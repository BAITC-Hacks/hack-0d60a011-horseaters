# Подготовка спроса ALG-01…ALG-05

`backend/domain/services/demand_preparation.py:prepare_demand` выполняет чистый
расчёт на существующих доменных сущностях. `PrepareDemand.execute` в application
загружает данные через текущий Unit of Work. SQLAlchemy, Pandas и сетевых обращений
в domain нет. Исходные сущности и `CalculationRun` не изменяются, результат не
записывается в БД, commit не вызывается.

## Вызов и воспроизводимость

У `CalculationRun.parameters` обязателен `demand_source`: `transactions` либо
`monthly_sales`. Набор `run.import_batch_ids` должен быть указан заранее. Use case
проверяет, что каждый импорт завершён и загружен не позднее `source_cutoff_at`.
Все связанные возвраты учитываются по дату среза включительно, даже если проведены
после последнего месяца рассчитываемого календаря.

```python
from datetime import date
from decimal import Decimal
from backend.application.use_cases.prepare_demand import PrepareDemand
from backend.domain.value_objects.demand import DemandConfig

# run.parameters["demand_source"] == "transactions"
# run.source_cutoff_at >= 2026-09-01T00:00:00Z, импорты зафиксированы в run
result = PrepareDemand(uow_factory).execute(
    run,
    start=date(2026, 1, 1),
    end=date(2026, 8, 31),
    groups=[(product_id, warehouse_id)],
    config=DemandConfig(growth_min_factor=Decimal("0.75"), growth_max_factor=Decimal("1.5")),
    # При необходимости: конкретная выбранная запись, без скрытого приоритета.
    # growth_assumption_ids={(product_id, warehouse_id): assumption_id},
)
```

Группы задаются явно: так результат включает и SKU/склад без единой продажи.
`Product` предоставляет SKU и единицу измерения; идентификаторы товаров/складов
сохраняются. `warehouse_id=None` разрешён только для месячного источника и остаётся
отдельной группой без распределения по складам и без компенсации stockout.

P0 поддерживает **полные календарные месяцы UTC**, с включённой последней датой.
Незавершённый месяц и агрегат, покрывающий неполный/несколько месяцев, отклоняются:
пропорциональное распределение без исходной детализации не выполняется. При
нескольких агрегатах одной группы за месяц требуется явно выбрать импорты.

Результат содержит параметры алгоритма, выбранный источник, границы истории,
дату среза, а в application также версию алгоритма и whitelist импортов. Вычисления
используют Decimal с precision=28 и ROUND_HALF_EVEN, стабильную сортировку и UUID5
для вычисленных аномалий/stockout. Округление до точности NUMERIC будущего хранилища
не выполняется; это отдельное решение при согласовании записи результатов.

## Этапы и принятые эвристики

1. **Источник и календарь.** Выбран ровно один источник для запуска. По каждой
   группе строится непрерывный ряд, отсутствующие месяцы получают ноль и
   `observed=False`. Транзакции никогда не складываются с месячными агрегатами.
2. **Возвраты.** Связанный возврат относится к месяцу исходной продажи, несвязанный
   — к собственному месяцу. Ссылка должна вести на более раннюю либо одновременную
   продажу того же SKU/склада. Отсутствие исходной продажи — ошибка, не повод считать
   возврат несвязанным. Возврат к продаже до начала календаря не уменьшает текущий
   месяц, что отражается в limitations. Превышение возвратами количества продажи
   отмечается; итоговый спрос периода ограничен нулём. Месячный источник может уже
   содержать нетто-количество: его возвраты не восстанавливаются и поправка равна 0
   с явным сообщением о недоступной детализации.
3. **Выбросы.** Для транзакций анализируется количество после связанных возвратов,
   отдельно по SKU/складу. Для агрегатов — положительные месячные количества.
   Нужны минимум 4 положительных наблюдения; календарные нули не используются как
   оценка обычного размера положительной отгрузки. Квантили линейно интерполируются
   по позиции `(n-1)*q`. Порог `Q3 + 1.5*IQR`; при IQR=0 защитный порог не ниже
   `median * 3`. Выброс заменяется медианой только в расчётной копии.
   Для реально заполненного `anonymous_customer_id` дополнительно проверяются
   месячные суммы клиента в той же группе, уже после очистки отдельных транзакций.
   Нужны 4 положительных месяца клиента. Аномальная сумма уменьшается до медианы,
   распределение по её транзакциям пропорциональное, повторного списания одной
   поправки нет. Покрытие клиентскими ID и недостаточная история явно отмечаются.
4. **Stockout.** Пересекающиеся imported/manual интервалы имеют приоритет; при их
   наличии в группе новые предположения по остаткам не выводятся. Иначе используются
   переданные inferred интервалы, затем история остатков. Для нового предположения
   нужны минимум 3 снимка, два соседних с `quantity_available <= 0`, расстояние между
   ними не более 45 дней. Интервал между ними имеет source=inferred и не считается
   подтверждённым. Это эвристика, а не доказательство непрерывного отсутствия товара.
   Пересечения объединяются, время отсутствия не учитывается дважды. Для компенсации
   используются минимум 2 из 4 ближайших месяцев этой же группы без stockout:
   есть факт спроса и либо положительный очищенный спрос, либо положительный снимок
   остатка. Отсутствие записи в календаре не делает месяц донором. База — медиана
   спроса в день, компенсация — база × дни отсутствия. Чужие SKU, сезонная коррекция
   и уже компенсированные периоды в эту базу не входят. Известная продажа без
   stockout трактуется как наблюдение доступного периода; это допущение отмечено
   здесь, а не гарантия непрерывной доступности. Без свидетельств и базы поправка 0.
5. **Рост.** После всех поправок сравниваются средние суточные значения двух
   соседних окон по 3 месяца (минимум 6 месяцев истории). Рост/снижение принимается,
   если хотя бы 2/3 последних месяцев подтверждают направление относительно
   предыдущего среднего. При короткой истории или нулевой базе factor=1 с причиной.
   По умолчанию factor ограничен [0.5, 2]; окна и границы настраиваются. Явно выбранный
   `GrowthAssumption` даёт factor=`1+growth_rate`; проверяются SKU/категория, склад и
   даты действия на момент среза. Скрытого выбора manual/imported либо SKU/category
   нет. Ограничение factor применяется и к явной записи, исходное значение и факт
   ограничения сохраняются.

Все численные параметры находятся в `DemandConfig` и копируются в результат.

## Разложение результата и ограничения сохранения

Каждый `PreparedDemandPeriod` содержит `raw_demand`, `return_adjustment`,
`demand_after_returns`, `anomaly_adjustment`, `nonnegative_adjustment`,
`stockout_adjustment`, `cleaned_demand`, `growth_adjustment`, `calculated_demand`.

```text
cleaned_demand = raw_demand + return_adjustment + anomaly_adjustment
                 + nonnegative_adjustment + stockout_adjustment
calculated_demand = cleaned_demand * growth.factor
```

Последнее значение — ряд, приведённый с учётом оценки роста, а не готовый прогноз
на будущий горизонт и не количество закупки. Сезонность, страховой запас и MOQ
в P0 не применяются. Детали содержат ID исходных строк, интервалы и источники
stockout, число дней, донорские месяцы и базовую ставку.

Транзакционные выбросы возвращаются существующими `DetectedAnomaly`: исходное
количество сохраняется, а `details.demand_before/demand_after` объясняют этап.
У `detected_anomalies.sales_transaction_id` обязательный FK, поэтому для месячного
источника используется отдельный аудит периода `PeriodAnomaly` в результате.
Создавать фиктивную транзакцию нельзя; для сохранения таких аномалий нужен отдельный
согласованный контракт. `DemandForecast` пока не создаётся: ещё не рассчитаны
сезонность и будущий прогноз, а его склад не допускает NULL.

Входные выгрузки ИЭК не использовались для проверки этой реализации. Клиентская
концентрация проверена **только на синтетических данных с обезличенным ID**;
при отсутствии этого поля в конкретной выгрузке проверка недоступна. Месячные
остатки не доказывают точные даты stockout. У ручных/вычисленных записей с NULL
импортом нет времени создания в текущем контракте: можно проверить даты действия,
но нельзя восстановить, была ли сама запись известна на историческую дату среза.
