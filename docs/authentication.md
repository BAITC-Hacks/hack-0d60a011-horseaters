# Локальная авторизация сотрудников

После миграции `alembic upgrade head` задайте в `.env` случайный `JWT_SECRET`
длиной от 32 байт (например, `python -c "import secrets; print(secrets.token_urlsafe(48))"`).
Шаблон из `.env.example` намеренно не принимается. Секрет должен быть одинаков
на всех экземплярах API и не должен попадать в Git. Срок JWT — 30 минут по
умолчанию (`JWT_ACCESS_MINUTES`, максимум 1440). Потеря секрета отзывает все
JWT после его замены.

Первого администратора создают вручную:

```powershell
python -m backend.infrastructure.bootstrap_admin --username admin@example.com
```

Команда запрашивает пароль без отображения. Публичной регистрации нет.

1. `POST /api/auth/login` с JSON `{"username":"admin@example.com","password":"..."}` возвращает `access_token`.
2. Передавайте `Authorization: Bearer <access_token>` на бизнес-запросах.
3. `GET /api/auth/me` показывает текущего сотрудника и роль.
4. Администратор создаёт закупщика через `POST /api/auth/users` с JSON `username`, `display_name`, `password`. Роль всегда `buyer`.

Смена пароля через API в MVP не предусмотрена.

Закупщик выполняет рабочий цикл, но утверждение заказа — только
`POST /api/orders/{id}/approve` с ролью `admin`. Администратор может просматривать
данные и создавать аккаунты закупщиков, но не выполнять операции закупщика.
JWT проверяется по подписи,
сроку, аудитории и эмитенту; при каждом запросе сверяется с активным
пользователем и версией его credentials в БД. Экспорт создаётся лишь для
утверждённого заказа. Отправки поставщику нет. Для production нужны HTTPS,
секрет из менеджера секретов, лимит запросов на вход и резервные процедуры
восстановления доступа.
