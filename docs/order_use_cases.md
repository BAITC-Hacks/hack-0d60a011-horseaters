# Корректировки и заказы: APP-06…APP-09

Все операции используют существующий `UnitOfWorkFactory`: одна сессия на вызов,
явный `commit()`, rollback и закрытие при выходе с ошибкой. Репозитории не делают
commit. ORM и миграции не изменены. Use cases возвращают доменные сущности или
внутренний DTO, не SQLAlchemy-объекты.

## Контракты

```python
AdjustRecommendation(uow_factory).execute(
    recommendation_id, expected_version=version,
    new_quantity=Decimal("15.0000"), reason="Изменился план", user_id=user_id,
)
CreateOrders(uow_factory).execute(calculation_run_id, user_id=user_id)
ApproveOrder(uow_factory).execute(order_id, user_id=user_id)
ExportOrder(uow_factory, XlsxOrderExporter()).execute(order_id, user_id=user_id)
```

В существующие `RepositoryFactories` нужно передать
`recommendations=SqlAlchemyRecommendationRepository`,
`orders=SqlAlchemyOrderRepository`, `products=SqlAlchemyProductRepository`,
`suppliers=SqlAlchemySupplierRepository`, `warehouses=SqlAlchemyWarehouseRepository`.
Остальные фабрики остаются прежними. Use cases получают только фабрику UOW;
Excel-адаптер внедряется через `application.ports.order_exporter.OrderExporter`.
После объединения с APP-01…APP-05 эти репозитории уже подключены в
`infrastructure.persistence.application_uow.create_application_uow_factory(database)`;
эту фабрику можно передать всем четырём use cases.

## Переходы и повторы

- Корректировка: `suggested | adjusted | accepted -> adjusted`, версия увеличивается
  на один. `rejected` и `converted_to_order` закрыты для корректировки. Каждое
  изменение создаёт отдельный `RecommendationAdjustment` с прежним/новым
  количеством, причиной, автором и временем. `recommended_quantity` не меняется.
- Создание: только положительные `accepted`, не присутствующие в строках заказов,
  переходят в `converted_to_order`; заказ создаётся только как `draft`.
  Группировка — поставщик + склад в пределах явно указанного запуска расчёта.
  Количества переносятся снимком. Все группы одного вызова фиксируются атомарно.
  Повтор после успешного создания возвращает пустой tuple; при конкурентном
  изменении возвращается конфликт, после которого можно повторить весь вызов.
- Утверждение: только `draft -> approved`, непустой заказ и положительные
  количества всех строк. Автор и UTC-время фиксируются вместе со статусом.
  Повторное утверждение отклоняется и не заменяет аудит первого.
- Экспорт: только `approved -> exported`, после готовности XLSX и вместе с записью
  `OrderExport`. Повторный экспорт отклоняется согласно текущей доменной модели.
  Отправки поставщику нет.

Ручные количества проверяются как конечные неотрицательные Decimal, представимые
в `NUMERIC(18,4)` без округления. Ноль допустим для корректировки, но не для строки
заказа. Обязательная кратность MOQ/упаковке для **ручной** корректировки в текущем
контракте отсутствует: автоматический расчёт округляет отдельно; ручной ввод не
округляется незаметно. Причина обязательна, максимум 2000 символов: это ограничение
существующей ORM (`VARCHAR(2000)`), хотя `docs/database.md` называет тип `TEXT`.

## Конкурентные операции

Предварительная проверка версии в application дополняется SQL compare-and-swap:
`UPDATE recommendations ... WHERE id = ... AND version = ... AND status ...`.
Дополнительно проверяются прежнее количество и отсутствие строки заказа.
Обновление ровно нуля строк вызывает `RecommendationConflictError`; аудит
добавляется только после успешного UPDATE в той же транзакции.

Создание сначала резервирует рекомендации условными обновлениями версии/статуса,
в стабильном порядке UUID, затем записывает заказы. При конфликте откатывается
весь вызов. Существующий UNIQUE по `purchase_order_items.recommendation_id`
остаётся последней защитой от дублей. Изменения количества через новый репозиторий
возможны только вместе с записью истории; метод сохранения конверсии количество
не меняет.

Утверждение и экспорт выполняют условный UPDATE по текущему статусу заказа.
Проигравшая конкурентная операция получает `OrderConflictError`; существующие
данные утверждения нельзя переписать через `save`. Это не требует нового поля
версии заказа или миграции. В PostgreSQL защита опирается на блокировку строки
при UPDATE и повторную проверку условия после ожидания. При уровнях изоляции,
которые возвращают serialization failure, вызывающий код должен повторить всю
транзакцию, а не отдельный SQL-запрос.

## XLSX и граница выдачи файла

`XlsxOrderExporter` формирует книгу полностью в `BytesIO`. Лист `Order` содержит
номер/ID заказа, код и имя поставщика и склада, дату утверждения, SKU, название,
единицу измерения, рассчитанное и утверждённое количества, необязательные цену и
сумму, ID рекомендации. Клиентские данные не читаются и не выгружаются. Строки
справочников записываются как текст, включая значения, начинающиеся с `=`.

Числовые значения представлены десятичным текстом с четырьмя знаками: Excel
сохраняет лишь 15 значащих цифр в числовых ячейках, а схема допускает 18. Это
сохраняет точные количества. Точный шаблон/порядок полей импортера 1С документацией
не задан; совместимость с конкретной конфигурацией 1С пока не проверена.

Use case считает SHA-256 **готовых байтов**, записывает аудит и новый статус,
делает commit и возвращает `ExportedOrder(metadata, content, media_type)`.
`metadata.file_name` — имя для скачивания, а не путь к файлу. Ошибка формирования,
записи метаданных или commit не возвращает результат; транзакция откатывается.
При вызове без `artifact_store` use case по-прежнему возвращает только байты.
Для HTTP в API-02 добавлен порт `ExportArtifactStore`: файл записывается до
фиксации метаданных в БД, POST создаёт экспорт, GET скачивает сохранённый файл.
Настройка хранилища и правила повторного скачивания описаны в
[`http_api.md`](http_api.md). Сбой доставки после успешного commit нельзя откатить
в рамках транзакции БД, но GET можно повторить. Текущий статус `exported` означает сформированный и
зарегистрированный экспорт, а не подтверждённую доставку файла.

Цена и сумма новых строк остаются NULL: согласованного правила выбора цены на
момент создания нет. Экспорт выводит их, если они уже сохранены в снимке строки.
Имена/SKU/единицы берутся из текущих справочников, поскольку схема сохраняет
снимками только количества и цены. Номер заказа — `PO-` + UUID, без придуманной
бизнес-нумерации.

## Авторизация и проверка

В проекте есть справочник пользователей и роли, но нет механизма проверки
полномочий или аутентификации. Новая система доступа не добавлена. Вызывающий
слой обязан передать UUID проверенного пользователя; существующие внешние ключи
обеспечивают наличие пользователя для аудита. Это не проверка его полномочий.

`tests/test_order_use_cases.py` использует отдельную временную SQLite-базу с
включёнными внешними ключами, реальные UOW и репозитории. Проверяются устаревшие
записи из разных сессий, атомарность, повторы, снимки, содержимое XLSX, SHA-256,
ошибки записи и commit. SQL compare-and-swap также компилируется для PostgreSQL.
Такие проверки не заменяют запуск конкурентных транзакций на реальном PostgreSQL.

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p test_order_use_cases.py -v
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -q
```
