# HTTP API — API-02

Маршруты подключены в `infrastructure/api/main.py`. Обработка HTTP, схемы Pydantic
и зависимости находятся в infrastructure. Роуты вызывают application use cases;
расчёт, корректировка, группировка заказов и смена статусов в них не дублируются.

## Маршруты

| Метод и путь | Use case | Успешный ответ |
|---|---|---|
| POST `/api/imports` | `ImportData` | 201, ID партии, статус, количество строк, checksum |
| GET `/api/imports/{batch_id}` | `GetImportStatus` | 200, безопасные сведения о партии и ошибках |
| POST `/api/calculation-runs` | `RunCalculation` | 201, сохранённый запуск |
| GET `/api/calculation-runs/{run_id}` | `GetCalculationRun` | 200, статус, параметры, ID импортов, число рекомендаций |
| GET `/api/calculation-runs/{run_id}/recommendations` | `ListRecommendations` | 200, `items`, `total`, `limit`, `offset` |
| GET `/api/recommendations/{recommendation_id}/explain` | `ExplainRecommendation` | 200, сохранённые формула, компоненты, прогноз, аномалии |
| PATCH `/api/recommendations/{recommendation_id}` | `AdjustRecommendation` | 200, актуальная рекомендация с версией |
| POST `/api/orders` | `CreateOrders` | 201, список новых черновиков |
| GET `/api/orders/{order_id}` | `GetOrder` | 200, заказ и строки со снимками количеств |
| POST `/api/orders/{order_id}/approve` | `ApproveOrder` | 200, утверждённый заказ |
| POST `/api/orders/{order_id}/export` | `ExportOrder` | 201, метаданные готового XLSX |
| GET `/api/orders/{order_id}/export` | `DownloadOrderExport` | 200, готовый XLSX без изменения состояния |

Перечисленные маршруты требуют проверенного активного пользователя. Health endpoints
остаются доступными без авторизации. OpenAPI — `/openapi.json`, Swagger — `/docs`.

## Пользователь и права

Существующий код не содержит проверки токена/сессии или identity provider. Поэтому
dependency `get_current_user` получает **доменный `User`** только из
`request.state.user`, заполненного доверенным серверным middleware, и по умолчанию
отвечает 403. Она не доверяет произвольному `X-User-ID`, Bearer-токену или полям
JSON. Для интеграции с внешней авторизацией можно заменить эту dependency адаптером,
который реально проверяет токен и получает пользователя. До подключения адаптера
бизнес-API намеренно не разрешает анонимные операции.

Активный `viewer` может читать данные и скачивать готовый файл. Изменения разрешены
`buyer` и `admin` через `require_writer`. Это минимальная проверка существующих
ролей, а не реализация новой системы входа. Проверка принадлежности объектов
организации не добавлена: такого контракта/поля в проекте нет.

ID автора берётся из dependency. JSON-запросы запрещают лишние поля, включая
`user_id`, `approved_by` и время действия. Устаревшее multipart-поле `imported_by`
не используется: фактический автор определяется проверенным пользователем.

## Входные данные

Импорт: multipart-поля `source_type` и `file`. Сохраняются существующие ограничения
`.xlsx`, непустой файл, до 25 МиБ. Роут ограничивает чтение размером лимит + 1 байт;
`ImportFileUseCase` повторно проверяет лимит, а `ExcelImportReader` — содержимое
книги и запрещённые персональные колонки. MIME от клиента не считается доказательством
формата. Имя нормализуется до имени файла без директорий. Multipart сначала
разбирается сервером с временным файлом; лимит общего HTTP body на reverse proxy
также следует настроить при развёртывании.

Запуск расчёта:

```json
{"horizon_days":30,"demand_source":"transactions","warehouse_id":null,"category_id":null}
```

`horizon_days` — положительное целое; `demand_source` обязателен, допустимы
`transactions` и `monthly_sales`. Значение передаётся в application DTO и сохраняется
в `calculation_runs.parameters`. Pipeline использует только выбранный источник;
автоматического fallback на другой источник больше нет. Для совместимости Python-
вызовов DTO по умолчанию выбирает transactions, но HTTP требует явного выбора.
Остальная методология APP-01…APP-05 не переписана: 365 дней истории, прогноз на
30 дней, 7 дней страхового запаса остаются текущими MVP-настройками.

Пагинация рекомендаций: `limit=1..500` (по умолчанию 50), `offset>=0`.
Фильтры: `supplier_id`, `warehouse_id`, `category_id`, `urgency`, `status`.
Сортировка: `risk_score`, `recommended_quantity`, `created_at`, `urgency`,
`product_id`; направление — `descending`.

Корректировка:

```json
{"new_quantity":"15.0000","reason":"Изменился план","version":3}
```

Количество передаётся Decimal, без потери точности; причина непустая, максимум
2000 символов, версия — положительное целое. Ответные количества также
сериализуются десятичными строками.

Создание заказов принимает `{"calculation_run_id":"UUID"}`. Согласно существующему
контракту выбираются все положительные принятые и ещё не заказанные рекомендации
запуска; произвольный список recommendation IDs пока не поддерживается. После
успешного вызова повтор возвращает пустой список. Отдельного HTTP/use case для
принятия рекомендаций пока нет: `AdjustRecommendation` оставляет статус `adjusted`,
он не подменяет принятие. Связать весь пользовательский процесс принятия следует
отдельной задачей.

Утверждение и создание экспорта принимают пустое тело или `{}`.

## Ошибки и приватность

Ошибки используют общий формат API: `{"detail":{"code":"...","message":"..."},"request_id":"UUID"}`.
Тот же ID возвращается в заголовке `X-Request-ID`. Валидация — 422, отсутствие ресурса —
404, конфликт версии/статуса 409, недостаток прав 403, недоступное хранилище/БД 503,
неожиданная ошибка 500. Ошибка сервера не превращается в успешный ответ. Если
`RunCalculation` возвращает сохранённый `failed` (например, нет импортов), POST
возвращает этот запуск с HTTP 422; GET такого запуска по-прежнему возвращает 200.

Валидационные ошибки импорта сохраняют ID неуспешной партии и номера проблемных
строк/отсутствующие канонические колонки. Значения ячеек и сырые исключения наружу
не выдаются. Request-validation ответы не повторяют входные значения. Параметры
запуска и компоненты объяснения имеют явные схемы; произвольные внутренние JSON-
диагностики, клиентские данные, SQL, пароль БД и пути файлов не сериализуются.

## Экспорт: команда и скачивание

APP-09 меняет статус, поэтому его вызывает **POST**, а не GET. POST полностью
формирует XLSX, вычисляет SHA-256 байтов, сохраняет файл и только затем фиксирует
метаданные/статус в транзакции БД. Существующий compare-and-swap статуса защищает
от повторного и конкурентного создания экспорта; проигравший получает 409.

Файлы хранятся через порт `ExportArtifactStore` и адаптер `FileExportArtifactStore`.
Настройка `ORDER_EXPORT_DIRECTORY`, по умолчанию `var/order-exports`, исключена из
Git. Имя файла на диске выводится из UUID экспорта, не из пользовательского пути.
Для нескольких workers/контейнеров требуется общий постоянный volume. Хранилище
не обслуживается статическим публичным маршрутом: GET сначала проверяет заказ и
запись экспорта, затем читает файл и сверяет checksum. При отсутствии/повреждении
зарегистрированного файла возвращает 503, не генерирует новый экспорт.

GET возвращает MIME
`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`,
`Content-Disposition: attachment; filename="order-<UUID>.xlsx"` и ETag checksum.
Его можно повторять: состояние и дата экспорта не меняются. До первого успешного
POST GET возвращает 404. `file_name` в метаданных — имя скачивания, не путь.

Файловая система и БД не образуют распределённую транзакцию: если запись файла
прошла, а commit БД не удался, остаётся невидимый GET незарегистрированный файл.
Он намеренно не удаляется автоматически, чтобы не потерять артефакт при неясном
результате commit. Нужна последующая уборка файлов без записей БД после проверки
активных операций. Ошибка записи файла оставляет заказ approved без аудита экспорта.
Точный шаблон 1С по-прежнему не согласован; используется существующий XLSX-адаптер.

## Проверки

`test_api_workflows.py` проверяет маршруты через dependency overrides без БД.
`test_order_use_cases.py` дополнительно проверяет POST/GET экспорта с настоящими
UOW, временной SQLite-базой и отдельным файловым каталогом: повторы, новый экземпляр
приложения, read-only GET, повреждение файла, ошибки хранилища и commit.
`test_application_calculation.py` проверяет фактическое разделение источников.

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -q
```

README, ORM-схема и миграции не меняются. Из недостающих HTTP-контрактов добавлены
минимальные `GetOrder`, `GetImportStatus`, `DownloadOrderExport`; обязательная
внешняя зависимость — доверенный адаптер аутентификации.
